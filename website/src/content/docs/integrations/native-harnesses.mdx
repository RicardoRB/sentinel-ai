Sentinel supports these project-local integrations:

| ID | Harness | Generated artifacts | Lifecycle coverage |
|---|---|---|---|
| `codex` | OpenAI Codex CLI | `.codex/hooks.json`, `.codex/hooks/sentinel.sh` | pre-tool, post-tool, feedback, approved-artifact guard |
| `cursor` | Cursor | `.cursor/hooks.json`, `.cursor/hooks/sentinel.sh` | pre-tool, file-edit, stop, feedback, approved-artifact guard |
| `copilot` | GitHub Copilot CLI | `.github/hooks/sentinel.json`, `.github/hooks/sentinel.sh` | pre-tool, post-tool, session, feedback, approved-artifact guard |
| `gemini` | Gemini CLI | `.gemini/settings.json`, `.gemini/hooks/sentinel.sh` | `BeforeTool`, `AfterTool`, agent/session feedback, approved-artifact guard |
| `windsurf` | Windsurf/Cascade | `.windsurf/hooks.json`, `.windsurf/hooks/sentinel.sh` | post-write, post-command, response feedback; no pre-tool enforcement |
| `cline` | Cline | `.cline/hooks/sentinel.json`, `.cline/hooks/sentinel.sh` | before/after tool, turn feedback, approved-artifact guard |
| `factory-droid` | Factory Droid | `.factory/plugins/sentinel.json`, `.factory/plugins/sentinel.sh` | post-tool, stop/session feedback; no pre-tool enforcement |
| `amp` | Amp | `.amp/plugins/sentinel.ts`, `.amp/plugins/sentinel.sh` | `tool.call` guard, `tool.result` feedback, `agent.end` continuation |

Install or remove one integration with:

```sh
sentinel integrate <agent>
sentinel integrate <agent> --remove
```

Generated files are project-local, ownership-marked, idempotent, and refreshed when Sentinel changes.
User-owned files are preserved as conflicts. The generated wrapper takes a phase argument:
`sentinel.sh pre` runs the approved-artifact guard (only when it is enabled) and `sentinel.sh post`
runs `sentinel hook native --agent <agent> --event-stdin`. Keep `sentinel` on `PATH`. Refreshing
without a guard option keeps the installed guard state.

## Verification status

Each adapter is being checked against the pinned harness release's documented contract
(`compatibility/manifest.json`). Until an adapter is listed as verified here, treat its generated
configuration as unverified: several adapters were found to write registrations in a shape their
harness does not read.

| ID | Pinned release | Generated-artifact tests | Live run |
|---|---|---|---|
| `amp` | Amp `0.0.1792123242-g03edc7` | Passing (`compatibility/amp`) | Not run: needs `AMP_API_KEY` |
| `codex` | Codex CLI `0.163.0` | Passing (`compatibility/codex`) | Not run: needs `OPENAI_API_KEY` and a hook-trust bootstrap |
| `cursor`, `copilot`, `gemini`, `windsurf`, `cline`, `factory-droid` | See `compatibility/manifest.json` | Not yet verified | Not run |

Every release runs these generated-artifact suites against the native executable it is about to publish
(Linux and macOS); a failing suite stops the release.

Generated-artifact tests execute the files that `sentinel integrate` writes, with a recording stand-in
for Sentinel. They prove the generated files have the documented shape and reach Sentinel correctly,
not that a running harness activates them; only a live run proves that.

## Codex

Sentinel writes `.codex/hooks.json` and the wrapper `.codex/hooks/sentinel.sh`. Codex reads `hooks.json`
strictly, so the ownership marker is stored in its `description` field. Codex runs project hooks only after
you review and trust them with `/hooks`; refreshing the integration changes the hooks, so Codex asks again.

| Codex event | Matcher | What happens |
|---|---|---|
| `PreToolUse` | `Bash`, `apply_patch` | With the guard enabled, asks Sentinel about the shell command or patch (`tool_input.command`) and denies protected changes with `permissionDecision: "deny"`. |
| `PostToolUse` | `apply_patch` | Runs the quality check. Failures exit `2`, so Codex gives the findings to the model. |
| `Stop` | | Runs the quality check and spec validation. Findings continue the turn once (`decision: "block"`); when `stop_hook_active` is set they are only reported. |

Commands are resolved from the repository root (`git rev-parse --show-toplevel`), so a session started in a
subdirectory still runs them. Integrations generated by Sentinel 0.0.7 and earlier were rejected by Codex
because of an unknown top-level field, so no hook ran; refresh with `sentinel integrate codex` and trust
the new hooks.

## Amp

Sentinel writes the plugin `.amp/plugins/sentinel.ts` and the wrapper `.amp/plugins/sentinel.sh`.
Amp loads project plugins only from the binary-installed Amp CLI (not the npm package or the editor
extension), and only when started with `PLUGINS=all`. In execute mode, add `--plugin-ready-timeout` so
the turn waits for plugins to load. Plugins run with your privileges; only enable them in trusted
workspaces.

| Amp event | What the plugin does |
|---|---|
| `tool.call` | For each file the call would modify, and for shell commands, asks the guard. A refusal returns `reject-and-continue` with Sentinel's reason. If Sentinel can't decide, the call is allowed and the reason is logged. |
| `tool.result` | After a successful call that modified files, runs the quality check (and spec validation for edited OpenSpec files). Failures are appended to the tool output the agent reads. Failed or cancelled calls are left untouched. |
| `agent.end` | When the turn ends with findings, continues the turn once with the findings (`maxContinuations: 1`), so an unfixable finding can't loop. |

Plugins generated by Sentinel 0.0.7 and earlier registered these events without calling Sentinel, so
no checks or guard decisions ran. Refresh with `sentinel integrate amp`, then restart Amp so it reloads
the plugin. To roll back, run `sentinel integrate amp --remove`; it deletes only Sentinel-owned files.

Capabilities are reported by `integrate` and `doctor`. Post-event-only harnesses are reported as
feedback-only; Sentinel does not claim pre-tool blocking where the native lifecycle cannot block.

Each native adapter parses its own payload aliases and maps its own lifecycle events into Sentinel's
normalized hook model. Denials are serialized using the harness response envelope: Codex uses
`hookSpecificOutput`, Cursor uses `permission`, Gemini uses `decision`, and Amp uses
`reject-and-continue`; the remaining advisory-compatible adapters use their documented decision
shape. Invalid or oversized payloads are treated as unreadable and never echoed in diagnostics.

Generated artifacts contain a Sentinel ownership marker. Re-running integration refreshes only
Sentinel-owned artifacts; unmarked files are reported as conflicts and remain unchanged. Removal
likewise deletes only owned configuration and wrapper files, preserving unrelated project content.
