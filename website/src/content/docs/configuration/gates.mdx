Every gate uses `[quality-gates.<id>]` with `command` (string or argument array), optional
`enabled` (default `true`) and optional `profiles` (default profile when omitted). The command
defines the actual tool invocation. Sentinel does not install gate tools during `check`.

| Category | ID | Tool | Typical purpose |
|---|---|---|---|
| Build & Tests | `compile` | Maven Compiler / Gradle compilation | Compile the project. |
| | `tests` | JUnit 5 | Run the project's automated tests. |
| | `coverage` | JaCoCo | Enforce or report test coverage. |
| | `mutation` | PIT | Run mutation testing. |
| Code Quality | `checkstyle` | Checkstyle | Check Java style rules. |
| | `pmd` | PMD | Find common Java design and implementation problems. |
| | `spotbugs` | SpotBugs | Run static analysis for potential bugs. |
| | `sonar` | SonarQube | Code smells, bugs, duplication, overall quality. |
| | `format` | Spotless / google-java-format | Check source formatting. |
| Security | `semgrep` | Semgrep | SAST and custom security rules. |
| | `gitleaks` | Gitleaks | Detect committed secrets. |
| | `dependency-check` | OWASP Dependency-Check | Scan dependencies for known CVEs. |
| | `zap` | OWASP ZAP | DAST against a running application. |
| | `trivy` | Trivy | Vulnerabilities in dependencies, containers, and IaC. |
| Architecture | `archunit` | ArchUnit | Run architecture rules/tests. |
| | `enforcer` | Maven Enforcer / Gradle checks | Dependency and build rules. |
| Dependencies & Compliance | `license` | License Maven Plugin / Gradle license plugin | License compliance. |
| | `api-compat` | japicmp | Binary/API compatibility between versions. |
| Custom | `command` | — | Run an arbitrary configured project check. |
| Traceability | `openspec-junit-traceability` | Sentinel source analysis | Require one explicitly annotated JUnit mapping per live OpenSpec scenario. |

The traceability gate is the one built-in gate that does not need a `command`:

```toml
[quality-gates.openspec-junit-traceability]
enabled = true
```

Each mapping must be directly declared on a `@Test`, `@ParameterizedTest`, or
`@RepeatedTest` method, using matching exact identities:

```java
@Tag("spec:identity/user-auth")
@DisplayName("Successful sign-in")
@Test
void signsIn() {}
```

Only mapping existence is checked; test execution and assertions are not. Empty
live specs fail with `no scenarios found`, and active-change specs are excluded.

`sentinel init` offers every gate but selects none by default unless a preset is chosen. `zap`, `trivy`, `sonar`,
`dependency-check`, `api-compat`, and `semgrep` need network access, a running application, or a
comparison baseline, so enable them deliberately (for example in a CI-only profile with
`profiles = ["ci"]`).

The Maven and Gradle `dependency-check` configurations read the NVD API key from the
`NVD_API_KEY` environment variable and never write the key to a build file. Without the variable,
scans may be very slow or rate-limited; request a key from the NVD API service.

Sonatype OSS Index requires credentials, so init turns the OSS Index analyzer off
(`<ossindexAnalyzerEnabled>false` on Maven, `analyzers { ossIndex { enabled = false } }` on Gradle).
To turn it on, set `OSS_INDEX_PASSWORD` (and `OSS_INDEX_USERNAME` if your token needs one) in the
environment and flip the setting. Gradle reads the variables directly. Maven reads credentials from a
`settings.xml` server whose id matches the generated `ossIndexServerId` (`ossindex`), so reference the
variables there instead of writing values to a file in the project:

```xml
<server>
  <id>ossindex</id>
  <username>${env.OSS_INDEX_USERNAME}</username>
  <password>${env.OSS_INDEX_PASSWORD}</password>
</server>
```

If you do not want to manage NVD or OSS Index credentials, the `trivy` gate also scans Maven and
Gradle dependencies for known vulnerabilities and needs no API key.

Standalone tools (`semgrep`, `gitleaks`, `trivy`, `zap-baseline.py`) must already be on the path; a
missing tool is reported as unavailable with an install link and other gates still run. `sentinel init`
can offer consented installation for supported tools, but `check` never installs them. When a command contains `--report-path <path>` inside the project, Sentinel
creates the parent directory before running it; the command itself is never changed.

## Structured findings

When `checkstyle`, `pmd`, `gitleaks`, `compile`, or `format` fails, Sentinel turns the tool's output
into findings with rule, severity, file, line, column, message, and a rule documentation link when
known. They appear in [JSON](/reference/json-output/) and SARIF output.

| Gate | Source | Maven | Gradle |
|---|---|---|---|
| `checkstyle` | XML report | `target/checkstyle-result.xml` | `build/reports/checkstyle/*.xml` |
| `pmd` | XML report | `target/pmd.xml` | `build/reports/pmd/*.xml` |
| `gitleaks` | SARIF report | `target/gitleaks.sarif` | `build/gitleaks.sarif` |
| `compile` | javac messages in the output | | |
| `format` | Spotless file list in the output (file only, no line) | | |

Only default report locations are read, and only reports written during the current run; an older
report is ignored. A missing or malformed report never changes the gate result: the gate just has
no findings. Gitleaks findings never contain the matched secret. Other gates have no findings yet.

## Partial checks

`sentinel init` writes a [`[quality-gates.<id>.partial]` table](/configuration/sentinel-toml/#partial-checks)
for `checkstyle`, `pmd`, `format`, and `semgrep`. After an agent edit, a gate is skipped when no edited
file is in its `inputs`, runs in full when one of its `config` files was edited, and is narrowed to the
edited files when the tool supports it:

| Gate | Maven | Gradle |
|---|---|---|
| `checkstyle` | `-Dcheckstyle.includes=**/<file name>` | `-PsentinelPaths=<paths>`, with a preset |
| `pmd` | full, with PMD's analysis cache | `-PsentinelPaths=<paths>`, with a preset |
| `format` | `-DspotlessFiles=.*/<path>`, a regular expression matched against the absolute path | full |
| `semgrep` | each path as its own argument | each path as its own argument |

The Gradle Checkstyle and PMD blocks init writes with a preset filter their sources to
`sentinelPaths` only when the property is set, so `checkstyleMain` and `pmdMain` still check the whole
`main` source set otherwise. Without a preset there is no filter, and those gates run in full. Gradle's
single-file Spotless mode applies formatting instead of checking it, so Gradle `format` runs in full.
The forms above were verified against the real tools: a path format a tool does not understand
analyzes no files and passes. The full check at the end of an agent turn, git hooks, and CI always
check the whole project.

For Maven-backed gates, `init` resolves a version from its embedded
Java/Maven compatibility catalog before adding a missing plugin to `pom.xml`. Existing compatible
versions are preserved; incompatible versions require confirmation, or `--yes` for explicit automation.
Unknown compatibility or an empty compatible catalog result stops before writing and reports remediation.
For Gradle projects, the same gate IDs map to Gradle tasks and pinned plugin declarations in either
the Groovy or Kotlin build script.

## Quality presets

`standard` enables compile, tests, format, Checkstyle, PMD, SpotBugs, and coverage with 70% line
coverage. `strict` adds ArchUnit, Enforcer, and PIT mutation testing; it requires 85% line, 75%
branch, and 60% mutation coverage. Strict mutation testing can substantially increase check runtime.
Preset initialization may write `config/pmd-ruleset.xml`, `config/checkstyle.xml`,
`config/spotbugs-exclude.xml` (standard), and `config/enforcer-rules.xml`. These files carry a
`managed-by: sentinel` marker; unmarked user files are never overwritten.

## ZAP target

`zap` requires an explicit target in its command. Init writes `<TARGET_URL>` as a placeholder; replace
it with an authorized target before running `check`, for example
`command = ["zap-baseline.py", "-t", "http://localhost:8080"]`. An enabled `zap` gate without
`-t <url>`, or still containing the `<TARGET_URL>` placeholder written by `init`, is a configuration
error (exit `2`). Sentinel never infers, starts, or scans a target on its own. You are responsible
for being authorized to scan the target.

The legacy identifiers `architecture` (use `archunit`) and `compliance` (use `enforcer`; license
checks now use `license`) remain readable for compatibility. Existing configurations need no change. Registry identifiers are validated by Sentinel; the configured command is the
gate-specific option and must be supplied. See [configuration syntax](/configuration/sentinel-toml/).

## OpenSpec tool validations

OpenSpec is an optional project tool, not a quality-gate menu entry. Configuration may register
the two validations independently:

```toml
[quality-gates.openspec]
enabled = true
command = ["openspec", "validate", "--all", "--strict", "--no-interactive"]

[quality-gates.openspec-archived]
enabled = true
command = ["openspec", "validate", "--archived", "--no-interactive"]
```

The configured executable is run directly from the target root; relative and absolute paths are
honored without PATH fallback. Both validations require a project-root `openspec/` directory.
Missing executables are reported as `UNAVAILABLE`; a missing or non-directory marker is a
reported `FAILED` result. Check and doctor never install or scaffold OpenSpec.
