![Four nested shields around your code: Edit, Commit, Push, and CI. Faster checks sit close to the code, stricter ones further out.](/sentinel-layers.svg)

AI coding agents write code faster than anyone can review it. Without guardrails, you repeat the
same rules in every prompt, and the agent still forgets some of them. Sentinel keeps those rules in
the repository and checks them at four moments, so the agent gets precise feedback early and nothing
it missed reaches production.

## The four layers

Each layer is a profile in [`sentinel.toml`](/configuration/sentinel-toml/). Inner layers are fast so
they can run constantly; outer layers are stricter and slower.

| Layer | Profile | When it runs | Set up with |
|---|---|---|---|
| **1. Edit** | `default` | After every agent edit or write | `sentinel init --integration <agent>` or [`sentinel integrate`](/commands/integrate/) |
| **2. Commit** | `pre-commit` | Before each `git commit` | `sentinel init --quality-hooks` |
| **3. Push** | `pre-push` | Before each `git push` | `sentinel init --quality-hooks` |
| **4. CI** | `ci` | In your CI pipeline | `sentinel init --ci github` or the [CI/CD guide](/guides/ci-cd/) |

### 1. Edit

After the agent edits or writes a file, its hook runs `sentinel check` on the edited files and returns
the result to the agent. A failure includes the file, line, and rule, so the agent can fix it in the
same turn without you explaining the rule. Only fast checks belong here, such as formatting,
Checkstyle, and PMD. See [Claude Code](/integrations/claude-code/), [OpenCode](/integrations/opencode/),
and [other agents](/integrations/native-harnesses/).

### 2. Commit

The `pre-commit` hook runs the same fast checks on the whole project. It catches what the edit layer
can't see: files changed outside the agent, by a person, or by a tool. See
[quality hooks](/integrations/quality-hooks/).

### 3. Push

The `pre-push` hook adds slower local checks before code leaves your machine: compilation, tests,
coverage, SpotBugs, and, with the `strict` preset, ArchUnit architecture rules and Maven Enforcer.

### 4. CI

CI runs every configured gate, including slow ones such as PIT mutation testing and the ones that
need network access, a running application, or a baseline, such as Trivy, Semgrep, OWASP Dependency-Check, SonarQube, and OWASP ZAP. This is
the last check before production.

## Layers are cumulative

`sentinel init` puts each gate in the first layer it fits and in every layer after it, so the outer
layers always include the inner ones. The bare `sentinel check` runs the same checks as `pre-commit`.
To move a gate, edit its `profiles` list:

```toml
[quality-gates.spotbugs]
command = "./mvnw spotbugs:check"
profiles = ["pre-push", "ci"]   # not on every edit or commit
```

## Why it saves time and tokens

- **The project explains the rules, not you.** The agent learns about a broken rule from a failing
  check, at the moment it breaks it, instead of from a long prompt.
- **Mistakes are fixed while they are small.** A finding on the edited file is cheaper to fix than a
  failed review or CI run hours later.
- **Repeated mistakes become rules.** With [learning](/configuration/learning/), a recurring finding
  asks the agent to write a preventive rule in `AGENTS.md`.

## Set it up with your agent

The [agent skills](/integrations/agent-skills/) let your coding agent set up the layers with you:
`sentinel-init` chooses the preset, gates, agent integration, and Git hooks for the project, and
`sentinel-tune` fits the rules to your real code.

## Share it with your team

Commit `sentinel.toml`, the rule files under `config/`, the generated agent hooks (such as `.claude/`
or `.opencode/`), and, if you generate it, `AGENTS.md`. Every teammate and every agent then works with
the same rules. The commit and push hooks live in `.git/hooks/`, which Git doesn't share; a one-step
setup for teammates is planned.
