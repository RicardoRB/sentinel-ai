# agent-integration Specification

## Purpose
Allow Sentinel to integrate with coding agents through explicit adapters while keeping quality-gate execution and result contracts independent of any specific agent.

## Requirements

### Requirement: Agent adapter boundary
Sentinel SHALL expose an agent adapter boundary that identifies supported agents and keeps agent-specific integration logic separate from project detection and quality-gate execution.

#### Scenario: Unsupported agent
- **WHEN** a user requests integration for an unknown agent
- **THEN** Sentinel reports the supported choices and exits with an actionable error

### Requirement: OpenCode integration
Sentinel SHALL support `sentinel integrate opencode` and SHALL detect integration points, avoid destructive overwrites, and clearly report files or settings changed.

#### Scenario: New OpenCode integration
- **WHEN** integration is requested for a detected project with no existing Sentinel integration
- **THEN** Sentinel creates only the required integration artifacts and reports the changes

#### Scenario: Existing OpenCode configuration
- **WHEN** integration encounters existing configuration that would be overwritten
- **THEN** Sentinel preserves it and requests explicit resolution rather than silently replacing it

### Requirement: Integration removal
Sentinel SHALL support `sentinel integrate opencode --remove` and SHALL remove only Sentinel-owned integration content.

#### Scenario: Remove owned integration
- **WHEN** removal is requested for an existing Sentinel integration
- **THEN** Sentinel removes Sentinel-owned content and preserves unrelated configuration

### Requirement: Agent-facing results
`sentinel check --format json` SHALL include, for each gate, a concise `summary` and relevant `output` suitable for an agent, and Sentinel SHALL NOT modify project source code itself.

#### Scenario: Failed gate for an agent
- **WHEN** a gate fails and JSON output is requested
- **THEN** the gate entry contains its status, exit code, summary, and captured output within schema version 1

### Requirement: Diagnostics
`sentinel doctor` SHALL check project detection, configuration, Maven and wrapper availability, enabled gates, agent integration, and native capabilities, reporting each finding as OK, warning, or error.

#### Scenario: Doctor on incomplete setup
- **WHEN** doctor runs on a project with missing or invalid prerequisites
- **THEN** it reports each issue with a useful remediation and exits according to the presence of errors

### Requirement: Edit/write integrations run Sentinel check with learning
The edit/write integrations generated by `sentinel integrate claude-code` and `sentinel integrate opencode` SHALL run Sentinel's quality check on the project with learning enabled at a default threshold of 3, as a direct argument vector rather than a shell expression. They SHALL NOT depend on a project-specific script such as `./verify-quality.sh`. The threshold SHALL appear as a visible `--learn-after` argument in the generated file, so users can change it.

#### Scenario: Claude Code hook after an edit
- **WHEN** Claude Code completes an Edit, Write, or MultiEdit tool call in an integrated project
- **THEN** the generated hook runs Sentinel's check with `--learn-after 3` from the project root

#### Scenario: OpenCode plugin after an edit
- **WHEN** OpenCode completes an edit, write, multiedit, or patch tool call in an integrated project
- **THEN** the generated plugin runs `sentinel check --format json --learn-after 3` from the project directory

### Requirement: Learning prompts reach the agent
Generated integrations SHALL pass learning prompts on to the agent whenever the check result contains them, including when every gate passes. Gate failures SHALL still be reported to the agent as failures. For Claude Code, a failing check SHALL be reported on stderr with exit code 2. A passing check with prompts SHALL produce `PostToolUse` hook JSON on stdout whose `additionalContext` contains the prompt text, with exit code 0. For OpenCode, prompts SHALL be appended to the tool result seen by the agent on success and included in the error on failure.

#### Scenario: Claude Code receives a prompt on a passing run
- **WHEN** a recurring error is resolved by an agent edit and all gates pass
- **THEN** the Claude Code hook exits 0 and prints valid `PostToolUse` JSON whose `additionalContext` asks the agent to add a preventive rule to `AGENTS.md`

#### Scenario: Claude Code failing run
- **WHEN** an agent edit leaves a gate failing
- **THEN** the Claude Code hook exits 2 and writes the failure details, plus any learning prompts, to stderr

#### Scenario: OpenCode receives a prompt on a passing run
- **WHEN** a recurring error is resolved by an agent edit and all gates pass
- **THEN** the OpenCode tool result contains the learning prompt text

#### Scenario: Nothing to report
- **WHEN** all gates pass and there are no learning prompts
- **THEN** the integrations add nothing to the agent's context

### Requirement: Upgrade of Sentinel-owned integration files
Re-running `sentinel integrate <agent>` SHALL replace Sentinel-owned integration files whose content differs from the current generated content and report them as changed. User-owned integration files SHALL be preserved and reported as conflicts, except that Claude Code settings SHALL be merged when valid JSON so unrelated user configuration is retained.

#### Scenario: Outdated owned hook
- **WHEN** a project has a Sentinel-owned Claude Code hook that calls `./verify-quality.sh` and the user runs `sentinel integrate claude-code`
- **THEN** the hook is rewritten with the current content and listed as changed

#### Scenario: User-owned file
- **WHEN** an integration target other than Claude Code settings exists without a Sentinel ownership marker
- **THEN** Sentinel leaves it untouched and reports a conflict

#### Scenario: Merge existing Claude Code settings
- **WHEN** `.claude/settings.json` contains valid user-owned settings or hooks and the user runs `sentinel integrate claude-code`
- **THEN** Sentinel adds its hook registrations while preserving all unrelated settings and hook entries

#### Scenario: Malformed Claude Code settings
- **WHEN** `.claude/settings.json` exists but cannot be parsed as valid JSON
- **THEN** Sentinel reports a conflict and leaves the file and other integration targets unchanged

#### Scenario: Remove Sentinel hooks from Claude Code settings
- **WHEN** the user runs `sentinel integrate claude-code --remove` on settings containing Sentinel and user-owned entries
- **THEN** Sentinel removes only its hook registrations and preserves the other settings and hooks

#### Scenario: Preserve settings file when no entries remain
- **WHEN** removal leaves `.claude/settings.json` with no Sentinel entries
- **THEN** Sentinel preserves the settings file, including when it contains no other settings
