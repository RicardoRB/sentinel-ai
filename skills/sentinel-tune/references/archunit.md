# Tuning ArchUnit rules

## Where the rules live

- Init generates `src/test/java/<package>/ArchitectureTest.java` only when no ArchUnit test exists.
  Once the file exists, it belongs to the user. Init never rewrites it and carries no ownership
  marker. When the project already had ArchUnit tests, init reused them instead, and the
  `[quality-gates.archunit]` command in `sentinel.toml` names those classes.
- The gate command runs the test classes by simple name, for example
  `./mvnw -Dtest=ArchitectureTest test`, or `./gradlew test --tests '*ArchitectureTest'` on Gradle. Moving a class to another
  package keeps working. **Renaming** it, or adding a new class, needs the command updated too. That
  edit is in `sentinel.toml`, and a later `sentinel init --overwrite` regenerates it.
- The `archunit-junit5` dependency is in the build file with test scope.

## Check what the generated test really analyzes

Read `@AnalyzeClasses(packages = "...")` and every `slices().matching("...")` pattern. Compare them
with the project's base package, the deepest package shared by all main sources. Init derives that
package from every main source, but a test generated by an older Sentinel, or later moved, can sit
in a sub-package such as `com.acme.shop.application`. Its rules then analyze only that sub-package
and pass without checking the rest. Fixing the package to the real base package is a
**strengthening**. Propose it first. It may produce findings that were hidden until now, so check
the layering below before running the gate.

## Gathering evidence from the code

Map the real dependencies between the top-level packages below the base package before proposing a
rule. For each pair of packages, count the imports:

```sh
grep -rhoE "^import <base>\.[a-z]+" src/main/java/<base-path>/domain | sort | uniq -c
```

Repeat this for each package. A small table of "from → to: count" is enough. Rules that the code
already obeys can be added without new failures. Rules it violates need the violations listed first.

## Typical proposals

| Proposal | When the evidence supports it | Class |
|---|---|---|
| Fix `@AnalyzeClasses` and slice patterns to the base package | The test analyzes a sub-package | strengthen |
| `layeredArchitecture().consideringOnlyDependenciesInLayers()` with explicit `whereLayer(...).mayOnlyBeAccessedByLayers(...)` | The packages map clearly onto layers, and the import table shows the direction | strengthen |
| `noClasses().that().resideInAPackage("..domain..").should().dependOnClassesThat().resideInAnyPackage("org.springframework..", "jakarta.persistence..")` | The domain has no framework imports today | strengthen |
| Naming rules, for example classes in `..infrastructure..` that implement a domain port end with `Adapter` | The code already follows the convention | strengthen |
| `GeneralCodingRules` such as `NO_CLASSES_SHOULD_USE_JAVA_UTIL_LOGGING` | No violations are found | strengthen |
| Remove a rule, or relax `should()` to fewer packages | Any reason | weaken |
| `FreezingArchRule.freeze(...)`, which records today's violations and fails only on new ones | Many existing violations, with the user's explicit agreement | weaken (it accepts existing violations) |
| Add `@ArchIgnore`, `DoNotIncludeTests`-style import options that drop production code, or `ignoreDependency(...)` | Any reason | weaken |

Keep rules in the existing test class unless the user asks for a new one. A new class needs the gate
command updated, as described above.

## Verifying

After an approved edit, run the test through Sentinel (see `SKILL.md`, Step 7). The `archunit` check
has no structured findings, so read its `output`. Each failing rule starts with a header line:

```text
Architecture Violation [Priority: MEDIUM] - Rule '<rule description>' was violated (N times):
```

Below it there is one line per violation, ending with the source location, for example
`Method <com.acme.shop.domain.Leak.type()> references class object <com.acme.shop.infrastructure.OrderController> in (Leak.java:11)`.
Repeat these lines to the user as evidence. Do not edit the rule to make them disappear.

A rule that matches no classes fails with `failed to check any classes`. That usually means the
`@AnalyzeClasses` package or a slice pattern is wrong (see above). It does not mean the code
violates the rule.

The generated layer rule ends with `.allowEmptyShould(true)`, because a new project may not have
classes in every layer yet. It starts checking as soon as classes appear there. Removing that call
is neutral when every layer it names already has classes. The cycle and coding rules keep the
default, so they still fail when the analyzed package is wrong.
