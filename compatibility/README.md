# Harness compatibility verification

Opt-in tooling that checks Sentinel's ten agent integrations against the harnesses they target.
It is separate from the Java build: `./mvnw -q test` needs no Bun, harness runtime, network access
or model credentials. The only part that runs in the Java build is
`CompatibilityManifestInventoryTest`, which fails when a registered adapter has no entry in
[`manifest.json`](manifest.json).

## Evidence levels

Every result records one of three evidence levels, and they are never interchangeable:

| Level | What runs | What it proves |
|---|---|---|
| `deterministic` | Artifacts generated by the real `sentinel integrate`, executed the way the harness documents launching them, with a recording `sentinel` stub on `PATH` | The generated registration has the documented shape, and its commands reach Sentinel with the expected arguments, stdin and working directory |
| `automated-live` | The pinned harness runtime, launched against a disposable fixture, discovering the generated artifacts on its own | The harness actually activates the integration and delivers feedback or refusals |
| `witnessed-live` | A person runs the documented editor procedure | The same as automated-live, for editor-only harnesses; recorded separately |

Deterministic evidence never counts as a live pass, and witnessed evidence never satisfies an
automated claim. Calling a hook command directly is not runtime discovery.

Each scenario ends as `pass`, `fail`, `blocked` or `unsupported`:

- A `pass` needs at least one executed assertion, all passing, from the pinned runtime version and
  the revision under test.
- A missing runtime, credential or editor, or an unimplemented driver, is `blocked`.
- `unsupported` is only valid when the manifest documents that the harness lacks the capability.
- A requested matrix exits non-zero unless every requested harness passes.

## Running the tooling tests

Build Sentinel first, since fixtures are generated by the real CLI (`target/sentinel`, or
`target/sentinel.jar` with `JAVA_HOME`, or an explicit `SENTINEL_COMPAT_SENTINEL`):

```sh
./mvnw -q package -DskipTests
cd compatibility
bun test test/
```

## All deterministic suites

`compatibility/run-deterministic.sh [path/to/sentinel]` runs the tooling tests and every harness suite
(`opencode-v2`, `amp`, `claude-code`, `codex`, `copilot`, `gemini`, `factory-droid`, `cursor`, `windsurf`, `cline`) against one Sentinel build. The release workflow runs it
against each Linux and macOS native executable before publishing, so a broken integration stops the release.

## Runtime preflight

Preflight locates each pinned runtime and checks its exact version. It never searches `PATH`, so
an unrelated global installation cannot satisfy it. A runtime is found either through its
`SENTINEL_COMPAT_<ID>_BIN` absolute path or in the isolated tools directory
(`compatibility/.tools`, ignored by git). `--install` performs only the manifest's pinned
`npm install --prefix` into that directory, with npm's cache and config inside the same directory.

```sh
cd compatibility
bun run src/cli.ts preflight all                  # report every runtime
bun run src/cli.ts preflight --install codex      # isolated pinned install, then check
SENTINEL_COMPAT_OPENCODE_BIN="$HOME/.opencode/bin/opencode" bun run src/cli.ts preflight opencode
```

The command prints one JSON line per harness and exits `1` unless every requested runtime is
`ready`. Version mismatches and failed installs are reported as `blocked` with the prerequisite.

## Witnessed Windsurf procedure

Windsurf runs Cascade hooks only inside the editor, so its live check is done by a person and recorded
as `witnessed-live` evidence, never as an automated pass. With Windsurf 1.126.0 signed in:

1. Build Sentinel and put it on `PATH`, then copy `src/test/resources/fixtures/maven-project` to a new
   directory and run `sentinel init` and `sentinel integrate windsurf --guard-approved-specs` in it.
2. Add `openspec/specs/smoke/spec.md` with any content and open the directory in Windsurf.
3. Ask Cascade to change `openspec/specs/smoke/spec.md`. Expected: the write is refused, Cascade reports
   Sentinel's reason, and the file is unchanged.
4. Ask Cascade to run `rm openspec/specs/smoke/spec.md`. Expected: the command is refused.
5. Create a file named `FAIL` in the directory, then ask Cascade to create `src/Smoke.java`. Expected:
   the file is written and the Cascade UI shows Sentinel's quality findings for the hook. The agent
   does not receive them; Windsurf has no hook output that reaches the model after an action.

Record the Windsurf version, the Sentinel revision and each step's outcome.

## Fixtures and isolation

`createFixture` copies the trusted offline Maven fixture (`src/test/resources/fixtures/maven-project`,
whose stub `mvnw` is the only command its gate runs) into a fresh temporary directory, then runs
the real `sentinel init` and `sentinel integrate <harness>`. HOME, XDG directories, `CODEX_HOME`,
`CLAUDE_CONFIG_DIR`, `COPILOT_HOME` and `TMPDIR` all point inside that directory, and `PATH`
contains only system directories. Every command runs as an argument vector in its own process group
with a deadline; the whole group is killed on timeout and when the command finishes. Failures
report only the step and exit status, never captured output, and evidence text is redacted and
bounded.

Never point the tooling at a user project. `sentinel.toml` is executable configuration.
